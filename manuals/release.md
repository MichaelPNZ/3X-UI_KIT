Репозиторий выпуска: [MichaelPNZ/3X-UI_KIT](https://github.com/MichaelPNZ/3X-UI_KIT).

Эти действия выполняет владелец после проверки рабочего дерева. Подготовка кода не
создаёт ключи, `SHA256SUMS`, подпись, коммиты, тег, release или deployment.

MichaelPNZ (28 октября 2026 года):

```text
ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIBtnfWRBFLYscAoCq2BZKttlax6YZ/QU7VQkNpIiO2gx 3X-UI KIT releases
```

Отпечаток: `SHA256:djDjuaSolHrl64v4UNojFoS2SLMK1ailFn0sNuLEPHo`.
Ключ уже создан владельцем; создавать или заменять приватный ключ для этого релиза не нужно.
Оригинальный ключ itsnotkubrick форк не принимает. Скрипт выпуска по-прежнему отклоняет
плейсхолдеры и некорректные публичные ключи, чтобы не выпустить будущую незавершённую сборку.

Путь приватного ключа по умолчанию — `~/.ssh/3x-ui-kit-release`; при обычной подписи
владелец может передать другой путь аргументом. Приватный файл и пароль остаются только
у владельца, вне репозитория и резервной копии VPS. В CI и на сервер они не нужны.
Подготовка релиза не читает приватный ключ и не подписывает manifest.

Перед подписью владелец сверяет свой публичный файл с отпечатком в KIT:

```bash
ssh-keygen -lf ~/.ssh/3x-ui-kit-release.pub
```

Оригинальные установки 1.2.x не доверяют этому ключу. Их ручной переход опубликован
в [README](../README.md#переход-с-оригинального-kit-12x) и должен применяться только после выпуска
подписанного тега `v1.3.0`. Это сознательная смена источника доверия владельцем сервера.

## Проверки и подпись

1. Убедитесь, что `VERSION` и `KIT_VERSION` трёх скриптов равны `1.3.0`, панель —
   `v3.11.0`, Xray — `v26.10.21`. Команды README и `manuals/3x-ui.md` должны ссылаться
   на `MichaelPNZ/3X-UI_KIT/v1.3.0`, CHANGELOG содержать `## v1.3.0`.
2. Проверьте diff, отсутствие посторонних изменений и приватных данных. Выполните
   локальные тесты и обязательный Linux CI. Для ручной проверки реальных клиентов
   используйте [описанные версии и настройки](panel-v3.11.0.md#клиенты-и-reality).
   Одного `run -test` или зелёного процесса Xray для подтверждения клиентов недостаточно.
3. После проверки владелец коммитит согласованные изменения. Скрипт подписи требует
   чистые файлы выпуска, чтобы подпись относилась к обозримому коммиту.
4. Владелец может сначала выполнить публичную проверку без чтения приватного ключа
   и без создания manifest/подписи, затем обычную подпись:

   ```bash
   tools/release.sh --check
   tools/release.sh ~/.ssh/3x-ui-kit-release
   ```

Скрипт отклоняет placeholder и проверяет формат публичного ed25519-ключа до сети
и любых операций с приватным ключом. Затем сверяет версии, ссылки, SHA официальных
sidecar-файлов и `assets[].digest` GitHub Release API, а также одинаковые суммы ядра
в установщике и updater. Только обычный запуск после этих проверок сверяет приватный
ключ с публичным и выполняет подпись.
После успешных проверок он создаёт `SHA256SUMS` с первой строкой:

```text
# 3X-UI KIT 1.3.0
```

В manifest входят файлы, перечисленные в `FILES` самого `tools/release.sh`:
установщики, `kit.sh`, `kit-sub.py` и `VERSION`. Скрипт подписывает manifest командой вида:

```bash
ssh-keygen -Y sign -f ~/.ssh/3x-ui-kit-release -n 3x-ui-kit-release SHA256SUMS
```

Получается `SHA256SUMS.sig`. Скрипт сразу проверяет подпись с identity
`releases@3x-ui-kit`, namespace `3x-ui-kit-release` и публичным ключом из KIT.
Не создавайте пустую подпись и не копируйте manifest оригинального релиза.
Не редактируйте подписанные файлы после этого: при любой правке manifest и подпись
нужно сформировать заново.

## Тег и GitHub Release

1. Владелец проверяет созданные `SHA256SUMS` и `.sig`, коммитит их и убеждается, что
   итоговый коммит содержит именно подписанные файлы.
2. После отдельного решения о публикации владелец публикует ветку/коммит в форк и
   создаёт тег `v1.3.0` на этом коммите. Существующий опубликованный тег не передвигать.
   В `main` также должны оказаться `VERSION=1.3.0` и соответствующий `CHANGELOG.md`:
   updater узнаёт последнюю версию из `main`, а подписанные файлы загружает из тега.
3. Создаёт GitHub Release для `v1.3.0` в `MichaelPNZ/3X-UI_KIT`, с предупреждением
   о смене ключа, ручном переходе и REALITY/ML-KEM. Прикладывает `SHA256SUMS` и `.sig`.
4. Проверяет доступность raw-файлов тега, `VERSION`, `CHANGELOG.md`, manifest и подписи
   с адресов форка, которые использует `kit`. Пока тег/подпись не опубликованы, команда
   установки `v1.3.0` из README не является готовым способом установки.
5. Включает private vulnerability reporting для форка и проверяет ссылку
   `Security → Report a vulnerability` из `SECURITY.md`.

`kit update` обновляет KIT/kit-sub по подписи; панель и ядро остаются прежними до
`kit panel update` и `kit core update`. Публикация KIT не является разрешением
на автоматическую смену ядра действующих серверов.

## GitHub Pages

Статические страницы уже лежат в корне репозитория: `.nojekyll`, `index.html`,
`tools/index.html`, библиотеки и переадресации `tools/xray/`, `tools/mihomo/`.
Корневой `index.html` отправляет к инструкциям на GitHub; генератор открывается
непосредственно по `https://michaelpnz.github.io/3X-UI_KIT/tools/`.
В репозитории нет отдельного workflow публикации Pages; CI сам сайт не развёртывает.

Владелец проверяет `Settings → Pages → Build and deployment`. Для имеющейся структуры
подходит `Deploy from a branch`: выбрать утверждённую ветку с файлами выпуска
(обычно `main`) и `/(root)`, сохранить. Папка `/docs` для этого дерева не подходит.
Если в настройках выбран GitHub Actions, нужен отдельный Pages workflow; текущий CI
его не заменяет. [Порядок настройки GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site).

После публикации открыть и проверить:

* `/3X-UI_KIT/tools/`, варианты `?core=xray`, `?core=mihomo` и `?router=openwrt`;
* `/3X-UI_KIT/tools/xray/` и `/3X-UI_KIT/tools/mihomo/` — переходы остаются внутри пути проекта;
* загрузку JS/CSS, создание/скачивание конфигов, ссылки на исходники форка;
* REALITY: `chrome` в Xray/sing-box и `support-x25519mlkem768: true` в Mihomo YAML.

Публикация Pages и проверка настоящих роутеров остаются отдельными действиями владельца.
